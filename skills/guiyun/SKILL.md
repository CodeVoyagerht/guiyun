# 归云 guiyun

**云端没有硬链接，所以每一次移动都要留退路。** 索引是真相，方案是预演，台账是反悔的凭据。

## 和归藏是什么关系

**一棵树，两个工具。** 本地库归 `guicang`（硬链接，原件不动）；网盘归 `guiyun`（真搬，留台账）。
但**分类规则只有一套**：都读同一份 `places.toml` / `activities.toml`，都按
「区域/活动/抖音 → 省/市（折叠）→ 地点/园区区域 → 年 → 备份周期 → 拍摄类型 → 机型（多才分）」落位。

所以网盘里看到的路径，和本地 `_归藏\` 里看到的**逐段同构**。这是天天明确要的：规则只有一套，别在哪儿看都是另一种分法。

网盘里的素材进库后长这样：

```
/摄影库/
├─ 区域/
│  └─ 郑州/                      ← 有两个以上城市时才出现这一层
│     └─ 泡泡塘森林溪谷/          ← 地点（places.toml 里的 name）
│        ├─ 水世界/              ← 园区区域（places.toml 里的 areas）
│        │  └─ 2024/
│        │     └─ 2024-05-18_05-24/   ← 备份周期：周六 → 周五
│        │        └─ 航拍/
│        │           └─ 2024-05-18 泡泡塘 水世界/   ← 整堆搬：RAW+JPG+SRT 不散架
│        └─ 露营区/
│           └─ 2024/2024-05-18_05-24/地拍/
│              ├─ Canon EOS R5/      ← 同一处同期真撞了两台机器，才多这一层
│              └─ SONY ILCE-7M4/
├─ 活动/
│  └─ 开封菊花文化节/
│     └─ 2024-第39届/              ← 届次从目录名认；认不出就用年份
│        └─ 2024/2024-07-06_07-12/航拍/
├─ 抖音/                          ← 抖音拍摄类自成一枝，不掺在区域里
│  └─ 2024/2024-08-03_08-09/地拍/
└─ 待定/                          ← 判不准的都在这儿，不瞎归
   └─ 2024/2024-06-01_06-07/地拍/
```

四件事先记住：

1. **方案是零副作用算出来的。** `scan` 把云端目录树抓进本地 SQLite 一次；`plan` 之后全在本机算，
   改主意、重算一百次也不花一次网盘请求。这不是优化，是保命——每次列目录都是一次可能被风控看见的调用。
2. **落位单位是「整堆目录 + 散文件」。** 没有子目录的文件夹整堆搬走（一次 `mv`），散落在别处的媒体文件
   一条条走。整堆搬能少一两个数量级的 API 调用，而且 RAW/JPG/SRT 不会散架。
3. **认不出来就进 `待定/`。** 云端读不到 EXIF，日期只能从目录名、文件名推；**用文件修改时间推出来的日期一律不许自动搬**
   （网盘的 mtime 常常是上传时间，照它分会把一次拍摄拆成几十个文件夹，比不整理还糟）。
4. **单值层自动折叠。** 只有一个省就不出现省份那一层；只有一个城市就不出现城市那一层；同一处同期只有一台机器就不出现机型层。
   **不用为了整齐去删空目录。**

分类法不是焊死的：清单目录、时间粒度、机型层开关、待定目录名，全在 `~/.guiyun/guiyun.toml` 里。
用户改主意只改配置，不重装。

## 什么时候用

| 用户说的是 | 用不用 | 怎么做 |
|---|---|---|
| "我网盘里素材太乱了，帮我理一下" | ✅ | 工作流 A |
| "按地点分，再按拍摄时间分" | ✅ | 工作流 A（就是默认分法） |
| "先把方案给我看看，别急着动" | ✅ | 工作流 A 走到 `plan` 就停 |
| "这条为什么进待定了" | ✅ | `guiyun explain <路径>` |
| "这个文件夹就是泡泡塘水世界，2024 年 5 月 18 号拍的" | ✅ | 工作流 B，`review --set` 钉住 |
| "这批是抖音的" | ✅ | 工作流 B，`--branch 抖音` |
| "上次整理我后悔了，退回去" | ✅ | 工作流 C，`guiyun undo <run_id>` |
| "整理完剩一堆空文件夹" | ✅ | 工作流 C，`guiyun clean` |
| "这张照片帮我调个色" | ❌ | 不是归类问题，直接说去 Lightroom / 达芬奇 |
| "帮我把这条片剪出来" | ❌ | 交给 `cutwright`，这里只负责把素材归好 |
| "本地硬盘里的素材库怎么归档" | ❌ | 那是 `guicang`（本地库，硬链接，不搬原件） |

## 铁律（不许跳）

1. **先 `status` 和 `scan`，再 `plan`。** 不知道配置、索引、上次整理是什么状态就动手，等于盲开。
2. **没把 `plan` 念给用户听，不许 `apply`。** `plan` 打出的树 + 条数 + 字节数就是念给他听的东西。
   他要的是「我的泡泡塘会变成什么样」，不是「已执行 7 条」。
3. **`apply` 真搬必须显式 `--yes`；第一次上手先 `--dry-run`，再 `--limit 5`。** 云端 `mv` 没有本地回收站那么顺手，
   先小批量试水，看着对了再全量。
4. **风控就是熔断，撞上立刻停手，不许重试硬刚。** 报「请求过于频繁 / 安全验证」（代码 132 / 112）时整批停，
   报出已经搬了几条、是什么挡住了、**后面还剩几条没轮到**。百度对异常调用量的惩罚是封号，不是限速。
   熔断后台账里那一行会写「整批在这里停下，后面还有 N 条没动」，`status` 也会显示「还有 N 条没轮到」——
   汇报时把这个数一起给用户，别说成"整理完了"。
5. **待定就报待定，不许瞎猜。** 一半素材落进待定，说明清单没配对——让用户补 `places.toml` 里的地名/别名，
   或者 `review --set` 一条条钉，别自己编地点名。
6. **不许说"整理好了"。** 要么给数字（搬了几条、几条待定、几个文件夹、多少 GB、run_id、任取一条完整路径），
   要么承认没验证。**交付必须带证据。**
7. **只搬不删。** `apply` 只做 move；`clean` 只删**空**目录，且必须 `--yes`。任何看起来要删素材的操作都先停下来问。

## 工作流 A：第一次接手一个乱网盘

```bash
guiyun init                       # ① 写 ~/.guiyun/guiyun.toml
# ② 打开它，把 [taxonomy] source 指到放 places.toml / activities.toml 的目录
#    （一般就是本地素材库的 .guicang，用 guicang init 生成）
guiyun login                      # ③ 百度网盘登录（BDUSS）
guiyun status                     # ④ 先看清单读没读到、索引/上次整理什么状态
guiyun scan                       # ⑤ 抓目录树进索引（只看不搬）
guiyun plan                       # ⑥ 出方案：树 + 条数 + 字节数（还是只看不搬）
guiyun review                     # ⑦ 看哪些钉不住，能钉的钉掉
guiyun apply --dry-run            # ⑧ 数一遍条数
guiyun apply --limit 5 --yes      # ⑨ 先搬 5 条试水
guiyun status                     # ⑩ 确认这 5 条对了，再 guiyun apply --yes
guiyun report --out 整理报告.md    # ⑪ 留一份台账
guiyun clean --dry-run            # ⑫ 搬空的源目录，看看要清多少
guiyun clean --yes                # ⑬ 真清（只删空目录）
```

`guiyun` 不在 PATH 时，**Windows 上用 `py -m guiyun`**（和 `guiyun` 完全等价）。
别用裸 `python` —— 在装了 Microsoft Store 版 Python 的机器上它是个什么都不做的占位程序，
调它只会安静地失败。Linux/macOS 上 `python3 -m guiyun` 即可。别在这上面卡住。

**清单目录是命门。** 归云自己没有项目表了，地点和活动的名字全在归藏那两份清单里：

```toml
# ~/.guiyun/guiyun.toml
[taxonomy]
source = 'D:\素材\.guicang'      # 里面要有 places.toml、activities.toml
```

- `places.toml` 一条地点四件事：`name`（落进目录的名字）、`aliases`（别名越多越好）、可选的
  `province` / `city` / `areas`（园区区域，写法 `"水世界|水上乐园"`）。
- `activities.toml` 一条活动：`name` + `aliases`，届次从目录名里的「第N届」自动认，认不出就用年份。
- **两份清单都没有工具也能跑**，但什么地点都认不出来，会全进待定。`status` 会直接告诉你缺哪一份。

`plan` 之后**别急着 apply**，先看两件事：

- **待定比例**。超过三成说明清单没配好，或者用户的目录名里根本没有地名（比如全是 `新建文件夹(3)`）。
  这时候要么补清单重扫，要么 `guiyun review` 逐条钉。
- **拍摄类型分布**。云端没有 EXIF，只能靠名字：目录/文件名里写了「航拍 / 地拍 / 延时 / 无人机 / 抖音」、
  写了机型（`Mavic 3`、`ILCE-7M3`），或者**同一堆里有同名 `.SRT`**（`DJI_0001.MP4` 配 `DJI_0001.SRT`），
  才判得比较有底。全靠 `.JPG` 三个字母的那种，拍摄类型往往只有 0.62，会进待定——**这不是 bug，是这条路的物理上限**，跟用户说清楚。

## 工作流 B：钉住待定（人工判定永远压过机器）

```bash
guiyun review                                             # 列待定，每条都带「钉住」命令模板
guiyun explain "/未整理/泉州西街"                          # 看它凭什么这么判
guiyun review --set "/未整理/泉州西街" --place 泉州西街 --shot 地拍 --date 2024-03-15
guiyun review --set "/未整理/泉州西街" --area 水世界        # 只补园区区域也行
guiyun review --set "/未整理/抖音竖屏" --branch 抖音        # 这批就是抖音的
guiyun review --set "/未整理/泉州西街" --date 2019          # 只知道年份也行，落 2019/
guiyun review --set "/未整理/截图" --clear                  # 撤掉人工判定，回到机器推断
```

- **只钉你知道的那几样**，剩下的机器照样补：钉了地点不钉日期，日期还是机器推的。
- 钉完**立刻重算方案**并打印那条的新结论（`→ 可自动搬：/摄影库/区域/泉州/泉州西街/2024/2024-03-09_03-15/地拍/泉州西街`），
  不用再跑一遍 `plan` 才知道效果。
- 钉的内容存在 `~/.guiyun/manual.json`，人是可以直接改的；下次 `scan` 也不会被覆盖。
- 日期认不出就**报错，不猜**：`--date 上个月那批` 会直接停下来说看不懂。

`explain` 的输出长这样，一眼能看出是哪条规则赢了、差在哪：

```
/未整理/泉州西街
  文件夹，2 个文件，42.92MB
  结论：待定
  去向 · 地点 泉州西街（0.90） · 拍摄 地拍 · 时间 2024/2024-03-09_03-15 · 机型 没认出来
  凭什么：
    · 只有修改时间 2025-03-01（网盘上可能是上传时间，不敢用）
    · 路径段「泉州西街」匹配地点 泉州西街（泉州西街）
  为什么不动：只有上传时间，没有能信的拍摄日期
```

## 工作流 C：反悔与收尾

```bash
guiyun status                     # 最近几次整理，每行都有 run_id
guiyun undo 20261115-210112       # 把那次 move 全部反向搬回去（按台账反序）
guiyun undo 20261115-210112 --dry-run   # 只数条数
guiyun clean --dry-run            # 整理后源目录剩的空壳
guiyun clean --yes
```

- `undo` **只信台账**（`index.sqlite` 的 runs/ops 表），不重新算方案。所以哪怕配置后来改了，
  撤的还是当时那批。
- `undo` 会自己重建原位置缺失的父目录——**先 `clean` 后 `undo` 也能还原**。
- `clean` 只删**一件东西都不剩**的目录，由深到浅（父目录要等子目录都没了才算空）。
  `scan_roots` 里那几个根本身永远不动；库根默认不碰（除非显式 `--root /摄影库`）。
- 百度网盘删的东西进**回收站**，真删错了还能去网页版捞回来。

## 工作流 D：换成本地同步目录（不登录也能跑整套）

```toml
# ~/.guiyun/guiyun.toml
[backend]
kind = "local"

[backend.local]
root = "E:\\网盘镜像"        # 这个目录就是后端的命名空间根：/摄影库 ↔ E:\网盘镜像\摄影库
```

```bash
guiyun status && guiyun scan && guiyun plan
```

适合：网盘客户端把云端挂成本地盘、或者用户干脆想先在一块测试盘上演练一遍。
**根目录里的路径全部按相对解释**，别指望它去解释 `D:\` 这种盘符——一份配置只认一个根。

## 判定规则速查

**分支**（谁先进谁赢）：

| 顺序 | 命中什么 | 权重 | 落到哪 |
|---|---|---|---|
| 1 | 路径含「抖音 / douyin / 竖屏」 | 0.90 | `抖音/年/周期/拍摄类型/` |
| 2 | 命中活动清单（置信 ≥0.70） | 0.78–0.90 | `活动/活动名/届次/年/周期/…` |
| 3 | 命中地点清单（GPS 或地名） | 见下 | `区域/省/市/地点/园区区域/…` |
| 4 | 都没有 | — | `待定/` |

**地点**（`places.toml` 里的名字与别名，比较前去掉空格/下划线/间隔号，忽略大小写）：

| 证据 | 权重 |
|---|---|
| 在坐标半径内（有 GPS 时） | 0.95 − 0.33×距离/半径（边缘约 0.62，进待定） |
| 路径段里出现地名 | min(0.88, 0.66 + 0.03×名字长度) |
| 完全等于正式名 | 该规则满分 |

**园区区域**：只在 `place.areas` 里找别名，命中给 0.90；**地点配了 areas 却一条都对不上 → 进待定**
（这是刻意的：分不清水世界还是露营区，就别硬塞）。

**时间**（从上往下第一条命中的赢；时间层默认是「年 / 周六→周五的周期」）：

| 顺序 | 证据 | 权重 | 能自动搬？ |
|---|---|---|---|
| 1 | 文件名里有 `2024-05-18` / `20240518` / `2024.5.18` / `2024年5月18日` | 0.95 | ✅ |
| 2 | 最近的上级目录名里有日期 | 0.95 − 0.04×层距（≥0.55） | ✅ |
| 3 | 目录名没日期，但**文件夹里所有文件名都写着同一天** | 0.85 | ✅ |
| 4 | 只找到年份 | 0.50（落 `年/`，不编周） | ✅ |
| 5 | 只有文件修改时间 | 0.45 | ❌ **一律进待定** |

第 3 条只要有一个文件名对不上就作废——半个拍摄拆成两半，比不整理更烦。
**周期固定是周六到周五**，跨年那一周整段留在起始年（2024-12-28 → 2025-01-03 落在 `2024/2024-12-28_2025-01-03`）。

**拍摄类型**（跟归藏同一套规则，云端只少了 EXIF 那几条）：

| 顺序 | 证据 | 权重 |
|---|---|---|
| 1 | 名字里有 FPV / Avata | 0.90 |
| 2 | 名字里有 延时 / timelapse / hyperlapse | 0.88 |
| 3 | 名字里有 航拍 / 无人机 / arial | 0.86 |
| 4 | 名字里有 地拍 / 手持 | 0.84 |
| 5 | 名字里有无人机机型（Mavic / Mini / Air / Phantom / Inspire / Matrice / Neo / FCxxxx） | 0.84 |
| 6 | 同一堆里有**同名 `.SRT`**（云端的遥测线索） | 0.80 |
| 7 | 名字里有地面机型（Sony / Canon / Fuji / Lumix / ILCE / EOS / X-T / Osmo / Pocket / iPhone） | 0.80 |
| 8 | 文件名是手机命名（`IMG_` / `PXL_` / `VID_` / 截图 / `mmexport`） | 0.80 |
| 9 | 文件名是运动相机命名（`GOPR` / `GX01` / `HERO`） | 0.80 |
| 10 | 文件名是相机命名（`MVI_` / `MOV_` / `DSC_` / `P1000123`） | 0.78 |
| 11 | 名字以 `DJI_` 开头但机型未知 | 0.55 |
| 12 | 什么都没有 | 0.50（进待定） |

8–10 号只在「读不到机型」时才生效：整堆搬时目录名不带这些前缀，归云会拿堆里**第一个媒体文件名**
顶上；`DJI_` 不参与前缀猜测（那是无人机），仍走 11 号进待定。

**机型**（只认名字里明写的，云端没有 EXIF）：落到路径里的是「厂牌 + 型号」，且**只有当同一个
（分支/地点/区域/周期/拍摄类型）下真的出现两台以上机器时才分层**。
整目录搬时，目录里那几个文件名也会参与认机型——目录名常常不含机型，但里面的 `DJI_0001.JPG` 含。

**能不能自己动手（`is_auto`）**：归藏判定为「自动」且 日期来源不是「修改时间」。
按年只能算到年的时间也允许自己搬（落 `年/` 那一层）。**日期这条卡得比地点还紧**，因为 mtime 的坑最致命。

细节（每个正则、每个阈值、`manual.json` 的格式）看 `references/evidence.md`。

## 常用命令

| 命令 | 干什么 | 动网盘？ |
|---|---|---|
| `guiyun init [--force]` | 写配置骨架 | 否（只写 `~/.guiyun/`） |
| `guiyun login [--bduss]` | 百度网盘登录 | 只登录 |
| `guiyun status` | 配置 / 清单 / 索引 / 上次整理 / 最近几次 run | 否 |
| `guiyun scan [--root R]...` | 抓目录树进索引 | **只读**（列目录） |
| `guiyun plan [--md F] [--json] [--all] [--detail N]` | 出方案、打目标树 | 否 |
| `guiyun review` | 列待定 / `--set --place --area --activity --branch --shot --date --camera` / `--clear` | 否 |
| `guiyun explain <路径>` | 一条凭什么这么判 | 否 |
| `guiyun apply --dry-run` | 数条数 | 否 |
| `guiyun apply [--limit N] --yes` | 真搬 | **是（move）** |
| `guiyun undo <run_id> [--dry-run]` | 反向搬回去 | **是（move）** |
| `guiyun clean [--root R] [--dry-run] [--yes]` | 清空壳目录 | **是（只删空的）** |
| `guiyun report [--out F] [--detail N]` | markdown 报告 | 否（`--out` 写一份文件） |
| `guiyun config` | 打印配置原文 | 否 |

`--home` 是**顶层**参数：`guiyun --home D:\test scan`（放在子命令前面）。也可以设 `GUIYUN_HOME` 环境变量。

`~/.guiyun/` 里有什么：`guiyun.toml`（配置）、`index.sqlite`（索引 + 台账）、`plan.json`（上次方案）、
`manual.json`（人工判定）、`runs/`。

## 常见坑

- **云端读不到 EXIF。** 日期和机型只能从目录名、文件名推。用户抱怨「怎么这么多待定」时，先看是不是这个原因，
  别去怀疑工具坏了。
- **文件修改时间不能当拍摄日期。** 网盘上的 mtime 往往是一次上传的时间。这是 `is_auto` 里唯一一条硬否决。
- **清单目录指错了 = 全线待定。** `status` 会打印「清单：N 个地点、M 个活动」，是 0 就说明 `[taxonomy] source` 没指对，
  或者那份 `places.toml` 的表头写错了（必须是 `[[place]]`，不是 `[[places]]`）。
- **`scan` 会跳过库根 `/摄影库`。** 否则整理结果下次被自己扫回去，越扫越乱。自己写脚本时也别越过这条线。
- **保险丝 20 万条。** 撞上会打印「只扫了一部分」，那不是错误，是刻意停的（一次扫太多容易被风控）。
  把 `[scan] roots` 收窄到真乱的那几个目录再扫。
- **扫描还有两个坑，现在都会报警。** ①`max_depth` 默认 8 层，更深的目录整棵不进去；
  ②某个目录读失败（刚被删、风控挡了一下）会被跳过。两种情况 `scan` 都会打「有 N 个目录…」，
  `status` 也会一直提醒，别把它当噪音——那批素材这次真没进索引。要补：调大 `max_depth` 重扫，
  或者把 `roots` 指到更深的那个目录。
- **`scan` 之后别手动改网盘。** 索引和云端对不上，`plan` 会算出目标已存在的假冲突。改了就 `guiyun scan` 重扫。
- **整理完索引就过期了。** `apply` 只打个 `stale` 标记，**不自动重扫**（那是几十上百次请求）。
  要接着整理就 `guiyun scan`。`status` 会提醒。
- **源目录会剩空壳文件夹（不是文件）。** 文件都搬走了，空壳得用 `guiyun clean` 清；不清也不影响正确性。
- **同名冲突默认改名**（`文件 (2).jpg`），不是报错。`plan` 里那个数字是「改名了」。
- **云端一次 `mv` 就能换目录+改名。** 但前提是目标路径本身不存在、父目录存在——所以工具总是先 `mkdir` 再 `mv`。
  别自己拼一个「移进去」的语义去调它。
- **路径里别出现 `*` `?` `[` `]`。** BaiduPCS-Go 会先做通配符匹配，文件夹名带方括号（`【2024】` 里没有，
  但 `[精选]` 有）会被当成模式匹配，报「未匹配到路径」。
- **BDUSS 等同于登录态。** 不要打进日志、不要写进报告、不要在对话里复述。`guiyun login` 用 getpass 输入。
